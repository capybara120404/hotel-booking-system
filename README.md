# Hotel Booking System

Система для бронирования отелей, разработанная на Spring Boot с использованием микросервисной архитектуры.

Система позволяет регистрировать пользователей, управлять отелями и номерами, создавать и отменять бронирования. Также реализованы автоматический подбор свободных номеров, защита от повторных запросов и обработка ошибок при взаимодействии между сервисами.

## Архитектура

Проект состоит из четырёх отдельных Spring Boot приложений:

- **Eureka Server** (порт 8761) - хранит информацию о запущенных сервисах и помогает им находить друг друга.
- **API Gateway** (порт 8080) - принимает запросы от пользователей, проверяет JWT-токены и перенаправляет запросы в нужный сервис.
- **Hotel Service** (порт 8082) - отвечает за отели и номера, проверяет их доступность и ведёт статистику бронирований.
- **Booking Service** (порт 8083) - отвечает за пользователей, авторизацию, создание и отмену бронирований.

Сервисы общаются между собой через REST API и используют Eureka для поиска друг друга.

Booking Service обращается к Hotel Service через `RestClient` с поддержкой балансировки запросов.

Схема работы:

`Client -> Gateway -> Eureka -> Target Service`

## Аутентификация

Для работы с системой используется JWT.

Пользователь регистрируется или входит в систему и получает токен. Этот токен нужно передавать в заголовке каждого защищённого запроса:

`Authorization: Bearer <token>`

Срок действия токена - 1 час.

### Публичные эндпойнты

- `POST /user/register` - регистрация пользователя.
- `POST /user/auth` - вход в систему.

### Регистрация

    curl -X POST http://localhost:8080/user/register \
      -H "Content-Type: application/json" \
      -d '{"username":"john","password":"secret123"}'

### Вход в систему

    curl -X POST http://localhost:8080/user/auth \
      -H "Content-Type: application/json" \
      -d '{"username":"john","password":"secret123"}'

## API

Все запросы выполняются через API Gateway.

### Booking Service - управление бронированиями и пользователями

| Метод  | Путь                 | Роль   | Описание                     |
| ------ | -------------------- | ------ | ---------------------------- |
| POST   | `/user/register`     | PUBLIC | Регистрация                  |
| POST   | `/user/auth`         | PUBLIC | Авторизация                  |
| POST   | `/api/bookings`      | USER   | Создание бронирования        |
| GET    | `/api/bookings`      | USER   | Просмотр своих бронирований  |
| GET    | `/api/bookings/{id}` | USER   | Получение бронирования по ID |
| DELETE | `/api/bookings/{id}` | USER   | Отмена своего бронирования   |
| POST   | `/user`              | ADMIN  | Создание пользователя        |
| PATCH  | `/user/{id}`         | ADMIN  | Изменение пользователя       |
| DELETE | `/user/{id}`         | ADMIN  | Удаление пользователя        |

При создании бронирования можно передать заголовок `Idempotency-Key`. Он защищает от создания нескольких одинаковых бронирований при повторной отправке запроса.

### Hotel Service - управление отелями и номерами

| Метод  | Путь                                       | Роль       | Описание                          |
| ------ | ------------------------------------------ | ---------- | --------------------------------- |
| POST   | `/api/hotels`                              | ADMIN      | Создание отеля                    |
| GET    | `/api/hotels`                              | USER/ADMIN | Получение списка отелей           |
| GET    | `/api/hotels/{id}`                         | USER/ADMIN | Получение отеля по ID             |
| PUT    | `/api/hotels/{id}`                         | ADMIN      | Изменение отеля                   |
| DELETE | `/api/hotels/{id}`                         | ADMIN      | Удаление отеля без номеров        |
| GET    | `/api/hotels/occupancy-stats`              | ADMIN      | Статистика бронирований           |
| POST   | `/api/rooms`                               | ADMIN      | Создание номера                   |
| GET    | `/api/rooms?startDate=&endDate=`           | USER/ADMIN | Поиск свободных номеров           |
| GET    | `/api/rooms/recommend?startDate=&endDate=` | USER/ADMIN | Получение рекомендованных номеров |
| PUT    | `/api/rooms/{id}`                          | ADMIN      | Изменение номера                  |
| DELETE | `/api/rooms/{id}`                          | ADMIN      | Удаление номера                   |

Рекомендованные номера сортируются по количеству бронирований: сначала идут номера, которые бронировали реже. Если количество бронирований одинаковое, используется ID номера.

### Внутренние эндпойнты

Hotel Service имеет три дополнительных запроса для общения с Booking Service:

- `/api/rooms/{id}/confirm-availability` - временно занимает номер.
- `/api/rooms/{id}/release` - освобождает номер.
- `/api/rooms/{id}/commit` - окончательно подтверждает бронирование.

Эти запросы нельзя вызвать напрямую через Gateway, так как они предназначены только для взаимодействия между сервисами.

## Создание бронирования

Для создания бронирования нужно отправить ID номера, дату заезда и дату выезда.

Пример:

    curl -X POST http://localhost:8080/api/bookings \
      -H "Authorization: Bearer $TOKEN" \
      -H "Idempotency-Key: unique-key-123" \
      -H "Content-Type: application/json" \
      -d '{
        "roomId": 1,
        "startDate": "2026-11-10",
        "endDate": "2026-11-15",
        "autoSelect": false
      }'

В этом случае пользователь самостоятельно выбирает номер.

### Автоматический подбор номера

Можно не указывать ID номера. Тогда система самостоятельно найдёт подходящий свободный номер.

    curl -X POST http://localhost:8080/api/bookings \
      -H "Authorization: Bearer $TOKEN" \
      -H "Content-Type: application/json" \
      -d '{
        "startDate": "2026-11-10",
        "endDate": "2026-11-15",
        "autoSelect": true
      }'

При автоматическом подборе система выбирает свободный номер с наименьшим количеством предыдущих бронирований.

## Как работает бронирование

Создание бронирования проходит в несколько этапов:

1. Booking Service создаёт бронирование со статусом `PENDING`.
2. Hotel Service проверяет, свободен ли номер, и временно занимает его.
3. Если номер свободен, Booking Service подтверждает бронирование.
4. Hotel Service сохраняет окончательную блокировку номера.
5. Бронирование получает статус `CONFIRMED`.

Если на одном из этапов возникает ошибка, система пытается отменить операцию и освободить номер.

Таким образом, номер не должен оставаться занятым, если бронирование не удалось завершить.

## Дополнительные возможности

### Защита от повторных запросов

Для защиты от дублирования используется `Idempotency-Key`.

Если клиент несколько раз отправит один и тот же запрос с одинаковым ключом, система не будет создавать новые бронирования.

Для этого используются уникальные ограничения в базе данных и внутренний `requestId`.

### Одновременное бронирование номера

Если несколько пользователей одновременно пытаются забронировать один номер на одинаковые даты, система проверяет пересечение дат и не позволяет создать конфликтующие бронирования.

Для этого используется отдельная таблица `room_locks` и блокировка записей в базе данных.

### Обработка ошибок

Если Hotel Service временно недоступен, Booking Service может повторить запрос.

Для этого используется Resilience4j:

- Retry - повторяет запрос до 3 раз с увеличивающейся задержкой.
- CircuitBreaker - временно прекращает запросы к сервису, если возникает слишком много ошибок.
- При недоступности сервиса клиент получает ответ `503 Service Unavailable`.

### Отслеживание запросов

Каждому запросу присваивается уникальный `X-Request-Id`.

Этот ID передаётся между сервисами и записывается в логи. Благодаря этому можно найти все сообщения, относящиеся к одному запросу.

### Автоматическая проверка бронирований

В системе есть фоновая задача, которая проверяет незавершённые бронирования.

Например, если во время создания бронирования произошла ошибка, система сможет найти такую запись и попробовать освободить номер.

Временные блокировки действуют 5 минут. Если бронирование не было подтверждено за это время, блокировка автоматически удаляется.

Подтверждённые бронирования при этом не затрагиваются.

## Структура баз данных

Каждый сервис использует собственную базу данных H2.

### База данных Booking Service

Таблица `users`:

- `id` - ID пользователя.
- `username` - логин.
- `password` - пароль.
- `role` - роль пользователя (USER или ADMIN).

Таблица `bookings`:

- `id` - ID бронирования.
- `user_id` - ID пользователя.
- `room_id` - ID номера.
- `start_date` - дата заезда.
- `end_date` - дата выезда.
- `status` - статус бронирования.
- `request_id` - ID запроса.
- `idempotency_key` - ключ для защиты от повторных запросов.
- `created_at` - дата создания.

Дополнительно используются уникальные ограничения:

- `request_id` должен быть уникальным.
- Пара `user_id + idempotency_key` должна быть уникальной.

### База данных Hotel Service

Таблица `hotels`:

- `id` - ID отеля.
- `name` - название.
- `address` - адрес.

Таблица `rooms`:

- `id` - ID номера.
- `hotel_id` - ID отеля.
- `number` - номер комнаты.
- `available` - доступность номера.
- `times_booked` - количество успешных бронирований.
- `version` - версия записи для проверки одновременных изменений.

Таблица `room_locks`:

- `id` - ID блокировки.
- `room_id` - ID номера.
- `start_date` - дата начала бронирования.
- `end_date` - дата окончания бронирования.
- `request_id` - ID запроса.
- `created_at` - дата создания блокировки.
- `expires_at` - время окончания блокировки.
- `status` - статус блокировки.

Для ускорения поиска используются индексы по отелям, номерам и датам бронирования.

Также есть ограничения, которые не позволяют создать два номера с одинаковым номером в одном отеле.

## Основные архитектурные решения

### 1. Сага вместо одной общей транзакции

Для бронирования используются несколько последовательных шагов.

Сначала Booking Service создаёт бронь, затем Hotel Service проверяет и временно занимает номер. Если всё прошло успешно, бронь подтверждается.

Если возникает ошибка, система выполняет обратное действие - освобождает номер.

Такой подход позволяет сервисам работать со своими базами данных независимо друг от друга.

### 2. Защита от повторных запросов

Для каждого запроса используются `Idempotency-Key` и внутренний `requestId`.

Это позволяет избежать повторного создания одного и того же бронирования, даже если клиент отправил запрос несколько раз из-за ошибки или таймаута.

### 3. Отдельная таблица для блокировки номеров

Для временного занятия номеров используется таблица `room_locks`.

Перед созданием блокировки система проверяет, нет ли другого бронирования на те же даты.

Для защиты от одновременных запросов используются блокировки записей в базе данных.

### 4. Проверка JWT в каждом сервисе

Каждый сервис самостоятельно проверяет JWT-токен.

Gateway также проверяет токены и блокирует доступ к внутренним запросам.

Это позволяет сервисам проверять права пользователей независимо друг от друга.

### 5. Обработка ошибок через Resilience4j

Если один сервис временно перестал отвечать, другой может повторить запрос или временно прекратить обращения к нему.

Это помогает избежать ситуации, когда ошибка одного сервиса приводит к проблемам во всей системе.

### 6. Общий ID запроса

Каждому запросу присваивается `X-Request-Id`.

Он передаётся между сервисами и используется в логах. Это упрощает поиск ошибок и отслеживание запросов.

### 7. Проверка незавершённых бронирований

Временные блокировки номеров действуют 5 минут.

Если за это время бронирование не подтвердилось, система удаляет такую блокировку.

Также фоновая задача проверяет бронирования, которые остались в статусах `PENDING` или `CANCELLING`.

Если обнаружена незавершённая операция, система пытается освободить номер и привести данные в порядок.

Эти решения помогают поддерживать согласованность данных, обрабатывать ошибки и обеспечивать стабильную работу системы.
